> 评审对象：`docs/evidence-chain.md`（v0.1）

## ① 总体结论

**结论：方向正确、值得实施，但当前 v0.1 方案**存在三处必须修正的硬伤**，不建议按原样直接进入实现。** 核心修正点见「④ 改进建议」的 P0/P1 项。修正后可按「⑤ 实施顺序」先行落地。

一句话判断：证据链是四象限里**杠杆最高、改动面最可控**的一步，思路（把黑箱判定变可审计输出）完全成立；但它目前**过度依赖 covers 自证、摘录定位无确定性规则、且没有真正解决它自己声称解决的 FN 可追溯问题**。这三处若原样落地，得到的将是「covers 声明=1.0 的伪可信 + 无法定位的摘录 + 只解决了一半的 FN」。修正后价值成立。

## ② 逐条裁决待评审的 6 个问题

### Q1. 证据模型（Evidence）是否遗漏关键字段？是否够支撑 8.5.2 置信度分层？

**结论：模型作 v1 种子基本够用，但为支撑 8.5.2 有明显缺口，且方案文档自身存在一处自相矛盾。**

现状（`plan.ts:77-85`）的 `targets` 只有 `{text, covered}`，新增 `Evidence` 是对齐校验输出的正确演化，方向对。但具体缺口：

1. **`status` 只有二态（'covered'|'not-covered'），无法表达 8.5.2 需要的第三态「partial / 需人工确认」。** 方案在 3.4 给「部分命中」打了 0.4 + `⚠需人工确认` 标记，但类型里没有承载这个标记的字段——`status` 塞不进去，只能硬塞进 `source.snippet` 的字符串，这在 `--json` 输出里是脏的、工具无法结构化消费。**建议：`status` 增加 `'partial'` 态，或新增 `needsReview: boolean`。** 否则 8.5.2 接门控时必然要再改一次模型（向后不兼容）。

2. **`matchKind` 是单值，无法结构化表达「双通道同时命中」。** 方案说「可合并、报告标注两路证据」，但类型里 `matchKind` 只能取一个值。**建议改为 `matchKind: MatchKind[]`（数组），或加 `corroborated: boolean`。** 这是后续置信度合成的关键信号，见 Q2。

3. **无版本/时间锚点。** 证据链的卖点是「可审计」。没有 `plan.md` 的 commit/哈希/生成时间，人只能证明「此刻这份 plan 里的命中」，无法证明「评审当时的那份」。**建议加 `planRef?: string`（git 短 sha 或文件 mtime）。** 对零依赖 CLI 来说取文件 mtime 就够，成本极低。

4. **方案文档内部矛盾（必须修）：** 3.1 写明「not-covered 或 confidence 过低时 `source = null`」，3.4 又要求「部分命中 → 0.4，`source.snippet` 标记需人工确认」。**低置信时 source 到底是不是 null？** 两处冲突。若按 3.1，partial 项没有 snippet，那「需人工确认的摘录」无从展示；若按 3.4，3.1 的 null 规则失效。必须统一为：`source` 只在「无任何命中」时为 null；有命中（含 partial）就非 null，靠 `status`/`needsReview` 表达「需确认」。

5. 次要：`targetId` 用「索引/文本」混着表示 FP 与 acceptanceCriteria，身份不唯一（`FP#3` 和 criteria 第三条都是「3」）。**建议 `targetId` 带类型前缀（如 `fp:3` / `ac:2`），否则 `--json` 消费方无法区分。** 这与 `planTargets`（`plan.ts:55-58`）把 FP 和 criteria 拼进同一数组的现状一致，正好在产出证据时补上身份。

**裁决：够起步，但 8.5.2 前必补 partial/needsReview + 通道数组 + 版本锚点；顺带修掉 3.1/3.4 的矛盾。**

### Q2. 双通道「取更高 confidence / 合并」是否合理？

**结论：当前「取更高」策略是错的，应改为「交叉佐证」的 AND 逻辑，而非 max。**

方案给 `explicit-covers = 1.0`、`text-match = 0.7`，双命中「取更高 → 1.0（来自 covers）」。这在语义上是**把最高可信度奖给了最不可信的证据源**：

- `covers` 是 **AI 的自我声明**（`planPrompt` 里明确要求它填 `covers:[...]`，见 `templates.ts`）。一个对抗性 agent 最省事的过关方式是**把所有 FP 原文塞进 `covers:`，正文什么都不写**——这正是 8.5.4 要防的「凑字面糊弄」，而方案却给它 1.0。**这在信任方向上完全反了。**
- `text-match` 至少是正文里出现了实质内容，比空声明可信。

**更优做法（推荐）：把两通道当作独立佐证信号，而非竞争信号，confidence 由「是否交叉印证」决定：**

| 组合                         | 语义             | 建议 confidence                |
| ---------------------------- | ---------------- | ------------------------------ |
| covers 命中 + 正文命中       | 声明被正文佐证   | 0.9~1.0（最强）                |
| 仅正文命中                   | 有实质内容       | 0.7                            |
| 仅 covers 命中（正文无佐证） | **自证，最可疑** | 0.4，`needsReview`（而非 1.0） |
| 都未命中                     | 未覆盖           | 0                              |

这样「取更高」变成「合并取佐证」，恰好利用了双通道的真实价值（互证），而不是简单 OR。**这是本方案最重要的置信度修正，直接影响 8.5.2。**「报告标注两路证据」这一点保留，是对的。

**裁决：保留「合并/双标」，推翻「取更高」。covers 不应默认 1.0，未获正文佐证时必须降级。**

### Q3. 「行号 + 章节」双定位 vs 仅「章节 + 摘录」，是否过度设计？对行号漂移哪个更稳？

**结论：不是过度设计，但行号必须是「尽力而为的次级参考」，不能当主锚；对漂移最稳的是「摘录」，其次是「章节」，行号最脆弱。**

- 稳定度排序：**摘录（内容锚，随编辑基本不变）> 章节（改名/重构才变）> 行号（任何一行插入/删除即漂移）**。
- 行号的价值：给编辑器/CI 一个可跳转坐标，计算成本极低（反正在按行解析）。**不是过度设计，前提是标注清楚「可能随编辑漂移」**——方案 3.3 已这么写，方向正确。
- 但有两个风险要压住：
  1. **别让行号参与匹配/哈希，只用于展示。** 若未来用「行号」去对账（比如增量校验 §8.5.5），漂移会导致误报。行号一律 match 时即时计算、不作为持久身份。
  2. **展示顺序：章节在前、行号殿后**，且摘录是主锚。方案里 `§<章节> L<起>-<止>` 这个格式把行号做成必选项，**建议让行号区间变为可选**（无行号时输出 `§章节 "摘录…"` 即可）。对人工复核，`章节+摘录` 已经足够定位；行号只是锦上添花。

**裁决：保留双定位但降级行号；以「章节+摘录」为主锚、行号标为参考且可选；禁止用行号做对账键。相对漂移稳健性：摘录 > 章节 > 行号。**

### Q4. 空/短证据降级是否足以防「凑字面糊弄」？

**结论：不足。空/短摘录降级抓不到真正的攻击形态，必须补「回声检测（echo detection）」。**

先看现实攻击（也是 8.5.4 adversarial 要抓的）：AI 在正文写「实现登录页重定向，未登录访问重定向到登录页。」——**这是完整、非空、长度远超任何「过短」阈值的句子**，且 `bodyNorm.includes(norm)`（`plan.ts:83`）必然命中 → 判 covered、confidence 0.7、snippet 正常长度 → **不会触发任何降级**。8.5.4 声称「只字面复述 FP 无方案应判 not-covered 或低置信」，但**当前设计的空/短降级规则对此完全无效**——它只拦「空或过短」，拦不住「字面复述但长度正常」。

**必须加的机制（零依赖、可自写）：回声检测。**

- 命中段落归一化后，若与目标文本的**归一化相似度/包含度极高、且周围几乎无额外实现性内容**，判为「echo 而非证据」，降级为低置信 + `needsReview`。判据示例：命中段归一化长度 ≤ 目标归一化长度的 1.3 倍，或命中段几乎完全由目标文本构成。
- 与 Q2 的「covers 需正文佐证」配合：正文命中若只是目标原文回声，不算有效佐证。

这才能兑现 8.5.4「把不被糊弄变成可测承诺」。方案里 `adversarial.test.ts` 写了目标但没给出达成目标的机制——**机制缺口在检测规则，不在测试本身。**

**裁决：空/短降级不足以防凑字面，需增加回声检测；否则 adversarial 测试目标无法达成。**

### Q5. 证据摘录截断策略（160 字符 + 上下文窗口）是否合适？

**结论：阈值合理，但「关键句」的选取无确定性规则，会破坏可复现性；截断要按句界而非字符。**

1. **160 字符**：终端一行展示的量级，合理。CJK 下约 160 汉字，够表达一句完整语义。**建议抽为具名常量**（如 `SNIPPET_MAX=160`），别散落硬编码。
2. **「首句或关键句」含糊。**「关键句」意味着选取逻辑，若不做规定，不同实现/不同运行可能选出不同句子 → 测试不稳定、CI 不可复现。**必须规定确定性规则：取命中段落的「首句」**（首个句号/换行前），稳定且可测。要更精确再演进。
3. **截断按句界：** 在 160 字符内从最后一个句号/换行符处截断，避免把 CJK 字符或单词拦腰截断。上下文窗口「前后各一句」保留是对的，与按句界截断天然一致。
4. 代码片段（plan 里常有伪代码）可能被截在语法中间——可接受，摘录只用于人工定位，不用于匹配。

**裁决：160 合理；但必须改为「命中段落首句 + 句界截断 + 具名常量」，删除「关键句」的非确定性表述。**

### Q6. 是否有更轻的落地路径？

**结论：有，可再砍一刀；但「按段定位」的重构是绕不过去的硬核，反而应在 v1 就做对。**

方案改动 7 个文件（含 templates、--json、adversarial）。更轻的路径：

**MVP（建议的 v1 范围）：**

- `types.ts` + `plan.ts` 产出每 target 的 `Evidence` + `renderer.ts` 输出一行证据行。**砍掉：`--json`（放 v2，但类型先定好）、`templates.ts` 倒逼自证（可选、默认关）、adversarial 全集（先补 Q4 回声检测的 1~2 条核心用例即可）。**
- 关键权衡：**定位必须基于「段落/章节级」匹配，而非现状的「整篇 bodyNorm.includes」**（`plan.ts:83`）。现状是一次全量 `includes`，**无法告诉你命中在哪一段**——这是证据提取绕不过去的重构，v1 就必须做（否则没有 location）。要警惕：改成按段匹配后，**跨段拼接才命中的目标可能不再命中，覆盖率数字会有微小变化**——这是预期内回归，须在测试里显式断言。
- 最轻又不自欺的方案：**v1 只输出「章节 + 摘录」，不带行号**（Q3 建议行号可选），进一步减掉行号提取的边界 case。

**裁决：可砍到 3~4 个文件（types / plan / renderer，+commands 若要做 --json 则 v2）。但按段定位的重构不能省，v1 就做。**

## ③ 发现的实质问题与风险（按严重程度标注）

### 🔴 P0（必须修正，否则方案不成立）

- **R1｜covers 通道信任倒置。** 给自我声明的 `covers` 无条件 1.0，等于把最高可信度奖给最易被对抗性 agent 利用的通道；且与 8.5.4「防凑字面」目标直接冲突。修正见 Q2/Q4。
- **R2｜声称的 FN 可追溯没被真正解决。** 方案 2 的目标明确写「FN 误报漏可追溯」，但 `Evidence` 只在 **covered** 时产出（`source` 在未覆盖时为 null）。**FN 恰恰是「明明覆盖却判未覆盖」——此时没有任何证据输出，人依旧要凭经验去 plan 里大海捞针。** 证据链实际只解决了「covered 的绿票可复核」，对 FN 反而帮不上忙。修正：为 not-covered 项也输出「最接近的近失（near-miss）」——扫正文里与目标归一化重叠度最高的段，报告「最接近的正文在 §X Lxx，但归一化未命中」，给人和 AI 一个追查入口。成本极小，价值是让「FN 可追溯」成真。
- **R3｜回声检测缺失 + adversarial 目标落空。** 见 Q4：空/短降级拦不住「正常长度的字面复述」，8.5.4 的承诺兑现不了。

### 🟠 P1（应修，影响质量与演进）

- **R4｜文档 3.1/3.4 关于 source 为 null 的自相矛盾。** 必须统一（见 Q1-4），否则实现者会做成两种行为。
- **R5｜`matchKind` 单值无法表达双通道佐证。** 改数组/加 corroborated 字段（见 Q1-2、Q2）。
- **R6｜按段匹配是未写明实细节的重构。** 现状全量 includes 拿不到位置；方案对「如何从整篇匹配迁移到段落级匹配」只字未提，且没提覆盖率微变风险。这是改动面里最不确定的一块，必须在方案里补「段落切分规则（以 #/## 标题为界）+ 跨段回归说明 + 对应测试」。
- **R7｜`0.4 partial` 档规则未定义。** 「部分命中 / 相似但归一化不含」——什么叫「部分」？没给规则就无法测试。要么给确定性判据（如部分 token 共现），要么 v1 砍掉该档，只留 covered/not-covered + 回声降级。

### 🟡 P2（改进项，不影响合入）

- **R8｜缺版本/时间锚点**（Q1-3），弱化了「可审计」卖点，建议加文件 mtime。
- **R9｜`targetId` 身份不唯一**（Q1-5），建议带类型前缀。
- **R10｜snippet「关键句」非确定性 + 非句界截断**（Q5），破坏可复现性。
- **R11｜8.5.1 与 8.5.2 的门控张力未显式说明：** 本版 partial(0.4) 的 `status` 若仍为 not-covered，则门控会 **block**（保守、安全），而 8.5.2 想要「非二元」；需在文档里写明「本版 partial ⇒ block，8.5.2 再改门控」，否则读者误以为 partial 能放行。
- **R12｜方案文档误置目标优先级：** 它把「FP 误放行有标记」做得很足，却把「FN 可追溯」列为同等目标——实际前者达成、后者未达成，文档结论与交付物不对称（同 R2）。

## ④ 改进建议（可落地的具体修改）

1. **【P0】重构 confidence 语义为「佐证强度」而非「单通道可信度」**（Q2）：covers 无正文佐证→0.4+needsReview；正文命中→0.7；双命中→0.9+。`matchKind` 改 `MatchKind[]`。
2. **【P0】新增回声检测**（Q4）：正文命中段若与目标归一化高相似且近无额外内容 → 判 echo → 低置信 + needsReview。零依赖自写。补 2 条 adversarial 断言。
3. **【P0】为 not-covered 输出 near-miss 近失线索**（R2）：报告「最接近的正文位置」，兑现 FN 可追溯。
4. **【P1】统一 source 语义**（R4）：仅「无任何命中」才 null；有命中即非 null，靠 status/needsReview 表达待确认。
5. **【P1】补充按段匹配设计**（R6）：以 `#`/`##`/`###` 标题切段、记录 L起-L止、明确跨段回归，并加测试断言覆盖率与旧逻辑一致或显式收敛。
6. **【P1】`status` 加 `'partial'` 或 `needsReview: boolean`**（R1），一次性对齐 8.5.2。
7. **【P2】`targetId` 带类型前缀；加 `planRef`（mtime）**（R9/R8）。
8. **【P2】snippet 规则定为「命中段落首句 + 句界截断 ≤160（具名常量）」**（R10），删「关键句」。
9. **【P2】文档显式写清**：本版 partial ⇒ 门控 block；templates 倒逼自证默认关闭、不进入 plan.md 契约必填项。

## ⑤ 是否建议先行实施 + 实施顺序

**建议先行实施。** 它是四象限里性价比最高的一步，方向正确、改动面收敛；但**必须先吸收 P0 三项修正（R1/R2/R3）再进实现**，否则落地即返工（尤其 confidence 语义与 model 的向后兼容）。

**推荐顺序（与方案 §8 基本一致，但重排）:**

1. `types.ts`：定 `Evidence`（含 `status` 第三态 / `matchKind[]` / `needsReview` / `planRef`，统一 source 语义）；
2. `plan.ts`：**先做按段切分重构**（拿到 location），再接入双通道证据产出 + 回声检测 + near-miss；
3. `renderer.ts`：一行证据行（`章节 + 摘录` 为主，行号可选）；
4. `commands.ts`：`--json` 可放 v2（类型先定好）；
5. 测试：三态 + 段定位 + 回声 + near-miss + 覆盖率回归断言；
6. 文档：更新 PROPOSAL §8.5.1 + CHANGELOG；
7. （v2）`--json`、templates 倒逼自证、partial 接入门控（8.5.2）。

**一句话：方向可投，但请把「covers 别给 1.0」「加回声检测」「FN 给近失线索」三条先缝进去再动手。**
